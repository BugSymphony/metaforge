# Feature Specification: 元数据全生命周期管理

**Feature Branch**: `001-metadata-full-lifecycle`

**Created**: 2026-08-01

**Status**: Draft

**Input**: 根据 Metaforge 元数据管理需求文档 V1.0（MVP版），生成 metadata-management 限界上下文的完整需求问题空间，覆盖实体元数据的草稿管理、版本生效与下线、结构合规校验、历史版本追溯、多维度查询检索、批量导入导出六大核心能力域。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 草稿管理与实时校验 (Priority: P1)

领域知识工程师基于已发布的 EntitySchema，创建新的实体元数据草稿。草稿完全隔离于正式版本，在草稿表中独立存储，对外不可见。每次保存时系统实时执行全字段 JSON Schema 结构校验——校验字段类型、必填项、枚举值、取值范围、正则格式、数组元素约束——仅校验通过的数据才允许写入。草稿可随时编辑和删除，直到工程师确认生效前，草稿不会对任何外部消费方（Agent、查询、关系构建）产生影响。

**Why this priority**: 草稿是元数据实例化的唯一入口，结构校验是所有写入操作的强制关卡。无草稿管理则无元数据，无结构校验则数据无质量保障——这是整个 BC 的基石能力。

**Independent Test**: 指定一个已发布的 EntitySchema，创建一条全新草稿并填入属性内容 → 保存成功写入草稿表 → 修改属性为违反约束的值 → 保存被拦截并返回结构化错误信息 → 删除草稿 → 确认草稿表无残留记录。全程主表无任何变更。

**Acceptance Scenarios**:

1. **Given** 已发布 EntitySchema `order:1.0.0.pkg_order.Order`，其 JSON Schema 要求 "orderId" 字段为必填字符串且匹配正则 `^SO-\d{6}$`，**When** 领域知识工程师创建草稿并填入 orderId="SO-123456" 及其他必填字段，**Then** 结构校验通过，草稿成功写入 metadata_entity_draft 表，主表无变化。
2. **Given** 上述草稿已存在，**When** 工程师将 orderId 改为 "INVALID"（不符合正则），**Then** 保存被拒绝，返回错误信息包含违规字段路径 `$.orderId`、违规类型 `pattern`、违反的元模型规则引用。
3. **Given** 草稿已存在且 FQN="SalesOrder_001"，**When** 工程师尝试用同一 FQN 创建第二条草稿，**Then** 系统拒绝写入，返回 FQN 重复冲突错误。
4. **Given** 草稿已存在，**When** 工程师执行删除操作，**Then** 草稿表对应记录被物理删除，该 FQN 可重新创建新草稿，主表与历史表无任何变更。
5. **Given** 已存在生效版本 FQN="SalesOrder_001"，**When** 工程师基于该生效版本创建修改草稿，**Then** 草稿内容从主表复制生成，base_version 字段记录原版本号，草稿写入草稿表，主表生效版本不变。

### User Story 2 - 版本生效与生命周期管控 (Priority: P1)

领域知识工程师对校验通过的草稿执行生效操作。生效为原子事务：同一事务内完成（1）主表写入/覆盖唯一生效版本、（2）全量快照归档至历史表（版本号递增）、（3）删除草稿表对应记录。任意一步失败，全量回滚不产生脏数据。生效后该 FQN 的版本成为所有对外服务的唯一基准。

对不再需要的生效元数据，工程师可执行下线操作。下线前系统自动校验：调用语义关系网络模块检查外部活跃引用、检查组合子实体是否有生效状态记录——存在任一拦截条件则拒绝下线并返回详细清单。下线同样是原子事务：从主表删除记录，历史表原样保留归档。

已下线的元数据可基于历史归档版本重新生效——无修改时直接恢复原版本，需修改则先创建草稿再走标准生效流程。

**Why this priority**: 版本生效是元数据从"编辑态"到"服务态"的唯一通道，决定了元数据对外消费的最终形态。无生效机制，所有元数据只是一堆草稿。与 P1 草稿管理共同构成"编辑→生效"的完整闭环。

**Independent Test**: 创建草稿 → 对草稿执行生效 → 验证主表出现唯一生效记录、历史表出现归档记录（版本号=1）、草稿表已删除该记录 → 执行下线 → 验证主表记录消失、历史表记录保持不变 → 基于历史版本重新生效 → 验证主表恢复、版本号保持 1。

**Acceptance Scenarios**:

1. **Given** 草稿 FQN="SalesOrder_001" 已通过结构校验，主表尚无生效版本，**When** 工程师执行生效操作，**Then** 主表新增记录（current_version=1），历史表插入版本快照（version=1），草稿表删除对应记录——三步在同一事务内完成。
2. **Given** 主表已存在生效版本 FQN="SalesOrder_001" (current_version=1)，草稿表有新版本的修改草稿，**When** 工程师执行生效操作，**Then** 主表记录被全量覆盖为新内容（current_version=2），历史表插入新快照（version=2），草稿表删除。
3. **Given** 生效操作进行中，**When** 事务中历史表归档步骤失败（如数据库连接异常），**Then** 主表写入与草稿删除同步回滚，主表保持原生效版本不变，草稿表保留未生效草稿，无任何脏数据残留。
4. **Given** 生效版本 FQN="SalesOrder_001" 被另一生效元数据 "OrderItem_005" 通过语义关系引用，**When** 工程师对 "SalesOrder_001" 执行下线，**Then** 系统拦截下线操作，返回引用清单（包含引用方 FQN="OrderItem_005" 及引用关系类型）。
5. **Given** 生效版本 FQN="SalesOrder_001" 下有生效子实体（FQN 前缀匹配），**When** 工程师尝试下线父实体，**Then** 系统拦截并返回生效子实体清单。
6. **Given** 已下线元数据 FQN="SalesOrder_001"（历史表 version=1 为最终版本），**When** 工程师执行无修改重新生效，**Then** 主表恢复历史归档记录，current_version=1，历史表不新增记录，该 FQN 恢复对外可见。

### User Story 3 - 多维度查询检索 (Priority: P2)

Agent 开发者、业务分析人员、平台管理员通过不同的查询模式获取元数据。默认对外查询仅返回主表中的生效版本——支持 FQN 精准查询、FQN 前缀范围查询（天然覆盖组合层级子树）、按元模型类型查询、属性条件组合查询（精准匹配/模糊匹配），结果支持分页与排序。

管理员可通过专属接口跨主表、草稿表、历史表聚合查询全状态数据（草稿、生效、下线），明确标注每条数据的来源表与当前状态。

**Why this priority**: 查询是元数据消费的入口，MetaForge 的核心价值——「Agent 可消费的结构化语义数据」——最终通过查询接口交付。查询能力直接决定消费方的使用体验。

**Independent Test**: 主表中准备 3 条 FQN 前缀为 "SalesOrder_" 的生效元数据 → 执行 FQN 前缀范围查询 "SalesOrder_" → 返回 3 条记录 → 执行 FQN 精准查询 "SalesOrder_001" → 返回 1 条完整详情 → 管理员执行全状态查询 → 返回草稿+生效+下线的聚合结果，每条标注状态。

**Acceptance Scenarios**:

1. **Given** 主表中存在 FQN="SalesOrder_001" 的生效版本，**When** Agent 通过 MCP 接口发起 FQN 精准查询，**Then** 返回该元数据的完整属性内容、关联元模型 FQN、当前版本号、审计信息（创建人、更新时间）。
2. **Given** 主表中存在 FQN 前缀为 "SalesOrder_" 的 5 条生效元数据，**When** 用户发起 FQN 前缀范围查询，**Then** 返回 5 条结果，包含 FQN、展示名、元模型类型、更新时间等摘要字段，支持分页。
3. **Given** 主表中存在 EntitySchema FQN="order:1.0.0.pkg_order.Order" 类型下的 10 条生效元数据，**When** 用户按元模型类型查询，**Then** 返回该类型下全部 10 条生效元数据，支持按更新时间倒序排列。
4. **Given** FQN="SalesOrder_001" 的 content 中 "status" 字段值为 "active"，**When** 用户按属性条件 `status = "active"` 查询，**Then** 返回所有 status 为 active 的生效元数据，支持模糊前缀匹配。
5. **Given** FQN="SalesOrder_001" 已下线（主表无记录），**When** Agent 执行 FQN 精准查询，**Then** 返回明确提示"该元数据不存在或已下线"，不泄露任何信息。
6. **Given** 草稿表、主表、历史表中各存在不同状态的数据，**When** 管理员调用全状态查询接口，**Then** 返回聚合结果，每条数据标注状态（草稿/生效/历史归档）及所属表来源。

### User Story 4 - 历史版本追溯与差异对比 (Priority: P2)

业务分析人员、领域知识工程师需要追溯某个 FQN 所有曾经正式发布过的版本记录，包括每个版本的生效时间与操作人。可按 FQN+版本号查询单个历史版本的完整属性快照。支持任意两个历史版本之间的字段级差异对比，按"新增字段、修改字段、删除字段"三类清晰展示变更内容。

**Why this priority**: 历史追溯是元数据治理的基础保障——当业务规则发生歧义或需要审计时，历史版本提供不可篡改的全链路追溯链。差异对比帮助理解版本演化轨迹。

**Independent Test**: 对 FQN="SalesOrder_001" 执行 3 次草稿→生效流程（产生 version 1,2,3）→ 查询全版本列表 → 返回 3 条记录按版本号倒序 → 查询 version=2 详情 → 返回完整属性快照 → 对比 version=1 与 version=3 → 返回差异对比结果（新增/修改/删除字段分类展示）。

**Acceptance Scenarios**:

1. **Given** FQN="SalesOrder_001" 在历史表中存在 version=1,2,3 三条归档记录，**When** 用户查询全版本列表，**Then** 返回 3 条记录按版本号倒序排列（3→2→1），每条包含版本号、生效时间、变更人，默认不返回完整属性内容。
2. **Given** 历史表中存在 FQN="SalesOrder_001" version=2 的归档记录，**When** 用户按 FQN+版本号查询详情，**Then** 返回该版本的完整属性快照、关联元模型 FQN、生效时间、操作人等全量信息。
3. **Given** version=1 的 content 为 `{"name":"A","value":10}`，version=2 的 content 为 `{"name":"B","value":10,"status":"active"}`，**When** 用户对比 version=1 与 version=2，**Then** 差异报告显示：修改字段 `name: "A" → "B"`，新增字段 `status: "active"`，无删除字段。
4. **Given** 用户尝试修改历史归档记录，**When** 执行 UPDATE 或 DELETE 操作，**Then** 数据库层面直接拒绝，返回不可修改错误。

### User Story 5 - 变更事件通知 (Priority: P2)

元数据生效或下线时，系统自动发布变更事件，通知下游语义关系网络模块、查询引擎模块同步数据，确保主表变更后整个平台的语义一致性及时收敛。

**Why this priority**: 变更事件通知是 metadata-management BC 与下游模块（关系网络、查询引擎）之间的松耦合协调机制，是实现「元数据变更 → 全平台感知」的一致性保障。

**Independent Test**: 执行一次草稿生效 → 验证变更事件已发布（包含 FQN、操作类型"生效"、版本号、时间戳）→ 执行一次下线 → 验证变更事件已发布（操作类型"下线"）。

**Acceptance Scenarios**:

1. **Given** 草稿 FQN="SalesOrder_001" 即将生效，**When** 生效原子事务成功提交后，**Then** 系统自动发布变更事件，事件内容包含 FQN="SalesOrder_001"、操作类型="生效"、版本号、时间戳。
2. **Given** 生效版本 FQN="SalesOrder_001" 即将下线，**When** 下线原子事务成功提交后，**Then** 系统自动发布变更事件，事件内容包含 FQN="SalesOrder_001"、操作类型="下线"、版本号、时间戳。
3. **Given** 生效事务中途失败回滚，**When** 事务回滚完成，**Then** 无变更事件发布。

---

### User Story 6 - 批量导入导出 (Priority: P3)

领域知识工程师需要从外部系统批量导入元数据，或导出当前生效元数据用于备份、迁移、多环境复制。导入支持 YAML/JSON 格式，以 FQN 为唯一标识，幂等支持"跳过"或"报错"两种策略。导入全程逐条执行结构校验，校验失败不影响其他合法数据。导入成功的数据仅写入草稿表，需手动执行生效。导出支持按 FQN 前缀范围、元模型类型、指定 FQN 列表三种粒度，导出格式与导入格式完全兼容，可直接重新导入。

**Why this priority**: 批量操作提升大规模元数据管理的效率，是生产环境中不可或缺的运营工具。但作为 MVP 的辅助能力，优先级低于核心生命周期管理。

**Independent Test**: 准备含 10 条元数据的 JSON 导入文件 → 执行批量导入 → 验证 10 条均写入草稿表、主表无变更 → 对其中 5 条执行生效 → 按 FQN 前缀范围导出 → 验证导出文件包含 5 条生效元数据且格式与导入文件兼容。

**Acceptance Scenarios**:

1. **Given** 导入文件包含 10 条元数据，其中 2 条 FQN 与主表已生效记录重复，**When** 工程师以"跳过"策略导入，**Then** 8 条新数据写入草稿表，2 条重复 FQN 自动跳过并记录在导入结果清单中。
2. **Given** 导入文件包含 10 条元数据，其中 1 条 content 违反 JSON Schema 约束（缺少必填字段），**When** 工程师执行导入，**Then** 9 条合法数据写入草稿表，1 条违规数据记录失败原因（违规字段路径+违规类型），其余合法数据不受影响。
3. **Given** 导入文件包含合法元数据，**When** 导入完成后，**Then** 所有数据仅存在于草稿表，主表无任何新增或修改，对外服务完全不受影响。
4. **Given** 主表中有 5 条 FQN 前缀为 "SalesOrder_" 的生效元数据，**When** 工程师按 FQN 前缀 "SalesOrder_" 导出，**Then** 导出文件包含 5 条元数据的完整属性、关联元模型 FQN、当前版本号，格式为标准化 JSON/YAML。
5. **Given** 刚导出的文件未做任何修改，**When** 工程师将其重新导入到同版本元模型环境中，**Then** 导入成功（或按策略跳过已存在的 FQN），导入格式与导出格式零转换适配。

### Edge Cases

- 当元模型版本升级（如 EntitySchema v1.0→v2.0）后，绑定 v1.0 的已生效元数据在主表"版本有效性校验"时如何处理？——标记为"元模型版本已升级"，允许继续对外服务，仅在重新生效时要求更新绑定。
- 当用户创建组合子实体草稿时，父实体在生效前校验通过但在生效事务中途被另一个并发请求下线，如何处理？——事务隔离级别保证生效操作的原子性，并发冲突由数据库唯一约束兜底。
- 当批量导入 500 条元数据时部分 FQN 格式不符合 `<segment>::=[A-Za-z][A-Za-z0-9_-]*` 文法，如何处理？——FQN 文法校验在 JSON Schema 校验之前执行，违规数据标记失败原因并继续处理后续数据。
- 当同时存在生效版本与草稿版本时，对外查询应返回哪个？——仅返回主表生效版本，草稿完全不可见。
- 当对父实体执行下线但存在已下线的子实体时，引用校验是否应放过？——仅检查生效态子实体，已下线的子实体不构成拦截条件。
- 当 FQN 中任意 segment 包含保留分隔符 `.` 时，写入阶段直接拦截，提示"segment 不允许包含保留分隔符 ."。
- 当父实体被下线但仍有生效子实体时，下线被 FR-019 拦截（检查生效子实体状态）。当 parent_fqn 指向不存在的父实体时，写入阶段校验直接拦截。

## Requirements *(mandatory)*

### Functional Requirements

**草稿管理**

- **FR-001**: 系统 MUST 支持基于已发布 EntitySchema 创建全新元数据草稿，草稿仅写入 metadata_entity_draft 表。
- **FR-001a**: 元数据实例 MUST 包含 `name` 字段作为必填的展示名称，不要求全局唯一。`name` 用于人类可读的展示标识，与 FQN 业务标识独立。
- **FR-001b**: 元数据实例 MUST 包含 `embedding` 字段（可选），类型为 JSONB 存储浮点数组。MVP 阶段仅保留字段不做维度校验与向量语义搜索，为后续扩展预留。
- **FR-001c**: 元数据实例 MUST 包含 `description` 字段（可选），用于补充说明元数据实例的业务含义与用途。
- **FR-002**: 系统 MUST 支持基于已生效版本创建修改草稿，内容从主表复制，base_version 记录原版本号。
- **FR-003**: 系统 MUST 在草稿创建时校验 FQN 全局唯一性（主表+草稿表联合查重），重复则拒绝写入并返回明确错误。校验前先验证每个 FQN segment 符合 `[A-Za-z][A-Za-z0-9_-]*` 且不含保留分隔符 `.`，违规则拦截。
- **FR-004**: 系统 MUST 支持对草稿态元数据的属性内容编辑（新增/修改/删除字段），编辑仅作用于草稿表。
- **FR-005**: 系统 MUST 禁止修改草稿的 FQN、parent_fqn 与 entity_schema_fqn 字段——创建后不可变更。
- **FR-005a**: 系统 MUST 在创建子实体草稿时校验 parent_fqn 指向的父实体已生效且存在——父实体未生效或不存在则拦截创建。顶级实体 parent_fqn 为 null。
- **FR-006**: 系统 MUST 支持物理删除草稿，删除后草稿表无残留，主表与历史表无变更。
- **FR-007**: 同一 FQN 在同一时刻 MUST 最多仅允许存在一条草稿，不支持多草稿并行编辑。

**结构合规校验**

- **FR-008**: 所有写入操作（创建草稿、编辑草稿、草稿生效、批量导入）MUST 实时调用对应版本 EntitySchema 的 JSON Schema 执行全字段结构校验。
- **FR-009**: 校验 MUST 覆盖字段类型、必填项、枚举值、取值范围、正则格式、数组元素约束等全部规则。
- **FR-010**: 校验失败时 MUST 返回结构化错误信息，包含违规字段路径（JSON Path）、违规类型、违反的元模型规则引用。
- **FR-011**: 校验逻辑 MUST 与 entity_schema_fqn 指定的元模型版本严格绑定，禁止跨版本使用校验规则。
- **FR-012**: 系统 MUST 在校验阶段同步校验组合父实体存在性与状态有效性——父实体未生效则拦截子实体创建。
- **FR-013**: 组合子实体 FQN MUST 自动按 `parent_fqn + "." + segment` 规则生成（segment 符合 `[A-Za-z][A-Za-z0-9_-]*`），无需手动填写全路径。parent_fqn 存储父实体的完整 FQN。
- **FR-014**: entity_schema_fqn MUST 携带完整版本号，禁止绑定草稿态元模型。
- **FR-014a**: 系统 MUST 提供统一的 FQN 生成器工具，具备以下能力：(a) 根据父 FQN 与当前编码生成完整 FQN（父 FQN + "." + 编码）；(b) 提取父 FQN（去掉最后一段）；(c) 按点分隔符拆分为段列表；(d) 提取顶级根实体 FQN（第一段）。

**版本生效与生命周期**

- **FR-015**: 生效前 MUST 执行全量预校验：结构合规校验 + 组合层级合法性校验 + 元模型版本有效性校验，全部通过后方可执行生效。
- **FR-016**: 生效操作 MUST 为原子事务：主表写入/覆盖 + 历史表归档（版本号递增）+ 草稿表删除，三步在同一事务内完成。
- **FR-017**: 事务任意一步失败 MUST 全量回滚，不产生任何脏数据，不影响主表原有生效版本。
- **FR-018**: 任意 FQN 在同一时刻最多仅存在一条生效记录——主表唯一生效版本原则。
- **FR-019**: 下线前 MUST 执行引用校验：检查外部活跃引用（调用语义关系网络模块）与生效子实体状态，存在任一拦截条件则拒绝下线。
- **FR-020**: 下线操作 MUST 为原子事务：删除主表记录，历史表原样保留归档，不做任何修改。
- **FR-021**: 系统 MUST 支持基于历史归档版本重新生效——无修改时直接恢复原版本号，需修改时先创建草稿走标准生效流程。

**历史版本追溯**

- **FR-022**: 历史表 MUST 仅支持 INSERT 操作，数据库层面禁止 UPDATE 和 DELETE。
- **FR-023**: 系统 MUST 支持按 FQN 查询全历史版本列表，按版本号倒序排列，包含版本号、生效时间、变更人。
- **FR-024**: 系统 MUST 支持按 FQN+版本号查询单版本完整属性快照、关联元模型 FQN、生效时间、操作人等全量信息。
- **FR-025**: 系统 MUST 支持任意两个历史版本的字段级差异对比，按"新增字段、修改字段、删除字段"三类分类展示。

**多维度查询检索**

- **FR-026**: 系统 MUST 支持通过 FQN 精准查询生效元数据完整内容，从主表读取。
- **FR-027**: 系统 MUST 支持 FQN 前缀范围查询生效元数据列表（天然覆盖组合层级子树），从主表读取。支持传入 FQN 前缀集合，按 OR 并集逻辑返回匹配任意前缀的所有生效元数据，结果按 FQN 排序，支持分页。
- **FR-028**: 系统 MUST 支持按 EntitySchema FQN 查询某类型下的所有生效元数据列表。
- **FR-029**: 系统 MUST 支持按属性条件（精准匹配/模糊匹配）组合查询生效元数据。
- **FR-030**: 查询结果 MUST 支持分页与按创建时间/更新时间排序。
- **FR-031**: 默认对外查询 MUST 仅返回主表生效版本——草稿不可见，历史版本不在默认查询范围内。
- **FR-032**: 系统 MUST 支持管理员专属全状态查询——跨主表/草稿表/历史表聚合结果，每条标注状态与来源表。
- **FR-033**: FQN 不存在或已下线时 MUST 返回明确状态提示，不返回空内容或泄露信息。

**变更事件通知**

- **FR-034**: 元数据生效事务成功提交后 MUST 自动发布变更事件（操作类型="生效"）。
- **FR-035**: 元数据下线事务成功提交后 MUST 自动发布变更事件（操作类型="下线"）。
- **FR-036**: 变更事件 MUST 包含 FQN、操作类型、版本号、时间戳。

**批量导入导出**

- **FR-037**: 系统 MUST 支持 YAML/JSON 格式批量导入元数据，以 FQN 为唯一标识。
- **FR-038**: 导入 MUST 支持"跳过/报错"两种幂等策略——已存在的主表生效 FQN 按策略处理，禁止覆盖主表。
- **FR-039**: 导入全程 MUST 逐条执行结构校验，单条失败不影响其他合法数据，返回导入成功/失败清单及失败原因。
- **FR-040**: 导入成功的数据 MUST 仅写入草稿表，需手动执行生效后方可对外可见。
- **FR-041**: 系统 MUST 支持按 FQN 前缀范围、元模型类型、指定 FQN 列表三种粒度导出生效元数据。
- **FR-042**: 导出格式 MUST 与导入格式完全兼容，导出的文件可直接重新导入。
- **FR-043**: 批量校验 MUST 支持按元模型类型或 FQN 前缀范围发起，输出校验报告（通过率+违规 FQN 清单+违规详情）。

### Key Entities

- **元数据实体 (Metadata Entity)**: 基于 EntitySchema 定义的具体语义实例，以 FQN 为唯一业务标识。核心属性包括：fqn（全限定名，全局唯一）、name（名称）、description（描述，可选）、parent_fqn（父实体完整 FQN，顶级实体为 null）、entity_schema_fqn（关联元模型全限定名含版本号，格式如 `order:1.0.0.pkg_order.Order`）、content（属性内容，符合 JSON Schema 约束）、embedding（向量嵌入，JSONB 存储浮点数组）、current_version（当前版本号）。存在三种生命周期状态：草稿态（仅存于草稿表）、生效态（存于主表且对外可见）、下线态（移出主表但归档于历史表）。

- **草稿 (Draft)**: 元数据实体的编辑态副本，存于 metadata_entity_draft 表，与正式版本物理隔离。属性包括：fqn（全局唯一）、name（名称）、description（描述，可选）、parent_fqn（父实体完整 FQN）、entity_schema_fqn、content、embedding（向量嵌入，JSONB 存储浮点数组）、base_version（可选，记录基于哪个正式版本创建）。草稿对外完全不可见，支持任意编辑与物理删除。

- **历史版本 (Entity Version)**: 元数据实体曾经正式生效过的版本快照，存于 entity_version 表。属性包括：fqn、version（递增整数，同 FQN 下联合唯一）、name（名称）、description（描述，归档时快照）、parent_fqn（归档时父实体 FQN 快照）、entity_schema_fqn、content（完整属性快照）、embedding（向量嵌入，JSONB 存储浮点数组）、created_by、created_time。历史版本仅可查看，不可修改或删除。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 单条草稿创建（含完整 JSON Schema 结构校验）从请求到存储完成的响应时间不超过 50ms。
- **SC-002**: 主表 FQN 精准查询从索引命中到返回完整内容的响应时间不超过 20ms。
- **SC-003**: FQN 前缀范围查询在返回百级结果集时，端到端响应时间不超过 100ms。
- **SC-004**: 单批次 500 条元数据批量导入（含逐条结构校验）总耗时不超过 5 秒。
- **SC-005**: 草稿生效原子操作（主表写入+历史表归档+草稿表删除）事务提交耗时不超过 100ms。
- **SC-006**: 单实体全历史版本列表查询响应时间不超过 100ms。
- **SC-007**: 全部写入操作的 JSON Schema 结构校验通过率达到 100%——不合规数据零容忍写入。
- **SC-008**: 草稿生效原子操作的原子性保障达到 100%——无部分生效、部分归档的中间脏状态。
- **SC-009**: 主表与历史表之间已生效版本的 content 数据一致性达到 100%——每次归档快照与主表写入内容完全一致。
- **SC-010**: FQN 全局唯一性约束保障准确率达到 100%——不存在主表/草稿表中重复 FQN 的记录。
- **SC-011**: 草稿与正式版本的隔离准确率达到 100%——所有对外查询接口不会暴露草稿表中的编辑态数据。
- **SC-012**: 批量合规校验能在 5 秒内完成 500 条元数据扫描并生成包含通过率、违规 FQN 清单、违规详情的校验报告。

## Clarifications

### Session 2026-08-01

- Q: 向量字段的名称、类型和存储格式？ → A: 字段名 `embedding`，类型 JSONB，存储浮点数组
- Q: name 字段的约束（必填性、唯一性）？ → A: 必填但不要求全局唯一，仅作为人类可读展示名称
- Q: FQN 统一生成器的解析能力范围？ → A: 支持提取父 FQN、分段拆分（按点分割为段列表）、提取顶级根实体 FQN
- Q: FQN 前缀集合过滤的语义？ → A: OR 并集过滤，返回匹配任意一个前缀的所有生效元数据，按 FQN 排序，支持分页
- Q: embedding 字段是否必填及是否需要维度校验？ → A: embedding 为可选字段，不做维度校验，MVP 阶段仅保留字段不做向量语义搜索，后续扩展
- Q: parent_fqn 与子实体 FQN 生成的关系？ → A: parent_fqn 存储父实体完整 FQN，子实体 FQN = parent_fqn + "." + segment。segment 符合 `[A-Za-z][A-Za-z0-9_-]*`，禁止包含保留分隔符 `.`。
- Q: entity_schema_fqn 示例格式需与 metamodel 对齐？ → A: 统一采用 `order:1.0.0.pkg_order.Order` 格式，与 metamodel BC 的 EntitySchema FQN 格式一致
- Q: description 字段是否必填？ → A: 可选字段，默认 null，用于补充说明元数据实例的业务含义

## Assumptions

- 元模型 EntitySchema 已由元模型治理 BC 完成定义、版本固化与发布，且通过 MCP/REST 接口可查询其 JSON Schema 与版本信息。
- 外部引用校验依赖语义关系网络 BC 提供查询接口——该接口返回指定 FQN 的所有引用关系清单（含引用方 FQN 与关系类型）。
- 变更事件通知依赖平台级事件总线（如消息队列或事件发布机制），本 BC 仅负责发布事件，不负责事件的持久化与重试。
- MVP 阶段采用单实例部署，不涉及分布式事务协调——生效原子性由数据库本地事务保证。
- 权限控制完全继承元模型的导入授权体系——本 BC 不做独立的细粒度权限校验，调用方的授权范围由上游网关或 Agent 消费接入层注入。
- 并发编辑冲突采用「最后写入覆盖」策略，不引入悲观锁或乐观锁机制。
- 历史表数据为永久保留策略，MVP 阶段不实现物理清理或归档转储功能。
- 导入导出文件格式默认为 YAML 与 JSON，不涉及 XML、CSV 等其他序列化格式。
- 组合层级关系的 Depth 理论上无上限限制，实际性能受 FQN 前缀索引与数据库递归查询能力的约束。
- 元数据实例 FQN（M1 层）与元模型元素 FQN（M2 层）分属不同层级：M1 FQN 采用点分隔层级路径（如 `Order.SalesOrder_001`），M2 FQN 采用冒号+点分隔格式（如 `order:1.0.0.pkg_order.Order`）。entity_schema_fqn 字段始终引用 M2 FQN 格式。

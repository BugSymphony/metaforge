## BC-Specific Principles

<!-- 本 BC 独有的核心原则，不从全局宪法继承。遵循 MUST/SHOULD/MAY 级别规范。原则名称不得与全局宪法原则重复。 -->

### I. 关系实例一等公民原则 (MUST)

关系实例是语义世界的一等公民，与实体元数据（metadata-management 管理的元数据实体）遵循完全统一的 FQN
全限定名体系、三表存储架构、生命周期流程和治理规则。关系实例不设置独立的命名空间、分类体系或权限模型，
所有语义归属与领域划分均由其关联的 RelationSchema 元模型定义。同一 RelationSchema 下，同一源实体与
同一目标实体之间仅允许存在一条生效关系。

### II. 三表正交存储原则 (MUST)

关系实例的存储必须采用「主表（`relation_instance`）+ 草稿表（`relation_instance_draft`）+ 历史表
（`relation_version`）」的三层正交架构，每张表仅承载单一状态，职责严格正交：
- **主表**：唯一可信正式拓扑数据源，仅存储当前生效的最新正式版本，对外默认可见。
- **草稿表**：编辑态隔离容器，仅存储未发布的关系草稿，对外完全不可见。
- **历史表**：永久只读归档库，仅存储曾经正式生效过的全量版本快照，不可篡改。

禁止在单表内通过状态字段混合多种状态，禁止跨表状态重叠。

### III. 结构合规强制校验原则 (MUST)

所有关系实例的写入操作（创建草稿、编辑草稿、草稿生效、批量导入）均须通过其绑定 RelationSchema
版本的 JSON Schema 全字段结构校验，校验覆盖字段类型、必填项、枚举值、取值范围、正则格式、数组元素约束
等全部规则。校验失败时返回结构化错误信息（包含违规字段路径、违规类型、违反的元模型规则引用），
校验不通过的数据直接拦截，禁止旁路写入主表与草稿表。

### IV. 双向索引事务一致性原则 (MUST)

关系生效时自动在源实体的出边索引和目标实体的入边索引中新增对应记录，关系下线时自动移除。索引的
创建与移除必须与关系生命周期变更（生效/下线）在同一数据库事务内完成，保证双向索引数据与主表正式
数据严格一致，杜绝索引遗漏或冗余。

### V. 原子生效与事务回滚原则 (MUST)

草稿生效为原子事务操作，同一事务内必须完成以下四步操作，任一步失败全量回滚，不存在中间脏状态：
1. 写入或全量覆盖主表对应 FQN 的记录；
2. 将该版本完整快照写入历史表（版本号递增）；
3. 删除草稿表中对应记录；
4. 更新双向引用索引（源实体出边 + 目标实体入边）。

### VI. 实体-关系拓扑同步原则 (MUST)

关系实例的生命周期必须与两端实体元数据的生命周期自动同步：
- 实体生效时，自动解析实体关联属性中的元模型关系引用，生成对应关系实例。
- 实体属性更新后重新生效时，自动增量新增、修改、销毁对应的关系实例。
- 实体下线时，自动校验该实体关联的所有生效关系，符合条件则同步触发关系下线。
- 自动构建的关系实例遵循统一的 FQN 生成规则（`{源实体FQN}.{关系类型编码}.{目标实体FQN}`），
  并自动执行完整的结构与拓扑校验。

同步操作须全程原子执行，杜绝实体已变更但关系未同步的中间不一致状态。

### VII. 历史版本不可篡改原则 (MUST)

所有曾经正式生效过的关系版本必须全量归档至历史表（`relation_version`），历史表仅允许执行
INSERT 操作，数据库层面通过权限配置禁止 UPDATE 与 DELETE。归档内容包括关系属性完整快照、
关联元模型 FQN（含版本号）、源/目标实体 FQN、版本号、生效时间、操作人。历史版本仅用于
追溯与版本对比，不作为对外拓扑查询的数据源。

### VIII. 草稿与生产物理隔离原则 (MUST)

所有关系编辑操作（新建、修改、删除）仅允许作用于草稿表，与主表正式版本完全物理隔离。
编辑过程不影响对外拓扑服务，对外查询默认仅返回主表中的生效版本。同一关系 FQN 最多仅允许
存在一条草稿，不支持多草稿并行编辑。草稿生效是草稿进入正式环境的唯一入口。

## 存储架构与数据模型

<!-- BC 专有的存储架构与数据模型约束，定义三表结构的核心字段与关键约束规则。 -->

### 关键数据约束

1. **FQN 全局唯一**：主表 `fqn`、草稿表 `fqn` 分别建立唯一索引，三方联合保证一个关系 FQN
   全局仅存在一条生效或一条草稿记录。

2. **元模型绑定**：每条关系必须关联一个已发布的 RelationSchema（`relation_schema_fqn` 含完整
   版本号），禁止绑定草稿态元模型。创建后元模型绑定不可变更。

3. **端点有效性**：关系生效时，源端和目标端实体必须处于生效状态，禁止指向不存在或已下线的实体。

4. **基数约束**：生效时基于 RelationSchema 定义的源端/目标端基数（1:1 / 1:N / N:M）实时校验，
   超出约束则拦截生效。

5. **跨域权限**：跨 Bundle 关系须符合元模型导出清单和依赖规则，未授权跨域关系自动拦截。

6. **Schema 隔离**：三张表均归属 `semantic_relation_network` 数据库 Schema，
   与其他 BC 逻辑隔离，禁止跨 Schema 直接写入。

## 核心能力与非功能约束

<!-- BC 核心能力的功能性约束与性能基线要求。 -->

### 核心能力约束

本 BC 对外提供以下核心能力，所有能力必须遵循本宪法中声明的原则与数据约束：

1. **草稿管理**：支持手动新建、基于生效版本创建草稿两种方式；草稿支持编辑与物理删除；
   编辑仅允许修改 `content` 属性内容，FQN、关联元模型版本、端点不得变更。

2. **自动边构建**：在 metadata-management 发布实体生效/下线事件时自动触发关系实例的生成、
   增量更新与销毁；原子事务保障实体与关系的一致性。

3. **版本生效与归档**：草稿→生效的原子升级流程，生成新版本号并归档。

4. **关系下线**：下线前执行依赖校验，存在强依赖则拦截并返回依赖清单；两端实体任意一方下线时
   自动触发关联关系下线校验。

5. **重新生效**：基于历史归档版本恢复为正式版本，支持直接生效或经由草稿修改后生效。

6. **基数管控**：生效、自动构建两个入口同步执行基数约束校验。

7. **拓扑完整性校验**：支持批量拓扑校验，检测悬空边、无效端点、基数超限、元模型不匹配四类问题。

8. **多维查询**：FQN 精准查询、实体出入边查询（按类型/实体类型过滤）、前缀范围查询、管理端
   全状态查询（草稿 + 生效 + 下线）。

9. **历史追溯**：按 FQN 查询全量历史版本列表、单版本详情、任意两版本字段级差异对比。

10. **批量导入导出**：YAML/JSON 格式，导入默认进入草稿态，禁止直接写入主表；幂等策略为
    「FQN 已存在则跳过或报错」。

### 性能基线（MVP）

| 指标 | 目标值 | 测量范围 |
|------|--------|----------|
| 单条草稿创建（含结构校验） | ≤ 50ms | 草稿表写入 + JSON Schema 校验 |
| FQN 精准查询 | ≤ 20ms | 主表唯一索引查询 |
| 单实体出入边查询 | ≤ 50ms | 百级结果集，双向索引驱动 |
| FQN 前缀范围查询 | ≤ 100ms | 百级结果集，普通索引扫描 |
| 批量导入（500 条） | ≤ 6s | 含逐条结构校验 |
| 草稿生效原子操作 | ≤ 100ms | 四步事务全程 |
| 全历史版本列表查询 | ≤ 100ms | 单 FQN 历史表扫描 |

### 一致性基线（MVP）

| 指标 | 目标值 |
|------|--------|
| 结构校验通过率 | 100%，不合规数据零写入 |
| 版本生效原子性 | 100%，零中间脏状态 |
| 主表与历史表版本一致性 | 100% |
| 双向索引与主表数据一致性 | 100%，零遗漏/冗余 |
| 实体与关系拓扑一致性 | 100%，零悬空边、零无效边 |

## MVP 边界与例外

<!-- MVP 阶段明确不实现的能力列表及其推迟理由。后续迭代可基于这些边界进行能力扩展。 -->

### 明确不实现

| 序号 | 能力 | 推迟理由与风险说明 |
|------|------|--------------------|
| 1 | 复杂图推理、深度路径计算、全链路血缘分析 | 归口 semantic-query-engine BC，本 BC 仅提供拓扑骨架数据 |
| 2 | 多版本并行对外发布、版本回滚 | MVP 阶段单版本即可满足拓扑确定性要求 |
| 3 | 草稿多版本历史、多草稿并行编辑 | 单草稿简化并发控制，避免锁机制引入 |
| 4 | 关系自动发现、LLM 智能补全 | AI 增强能力后置于核心链路验证 |
| 5 | 关系权重、置信度、时效属性管理 | 超出 MVP 关系类型定义范围 |
| 6 | 增量同步、变更事件主动推送 | MVP 使用 Spring ApplicationEvent 内存事件，同步模式 |
| 7 | 多租户隔离、全链路操作审计 | MVP 单租户部署，审计由基础设施层统一提供 |
| 8 | 审批工作流、字段级细粒度权限 | 权限继承元模型与实体导入授权，不做独立细粒度管控 |
| 9 | 关系跨元模型版本自动迁移与兼容性转换 | 元模型升级后存量关系需手动迁移 |
| 10 | 关系元数据独立命名空间 | FQN 统一承载层级、归属与唯一性 |

### 不引入的外部依赖

- 消息队列（RabbitMQ / Kafka）：MVP 使用 Spring ApplicationEvent 内存事件
- 图数据库（Neo4j）：MVP 使用 PostgreSQL 邻接表 + 递归 CTE
- 外部缓存中间件（Redis）：MVP 使用 Caffeine 本地缓存

## BC Overrides

<!-- 选择性覆盖父全局宪法中的 SHOULD/MAY 级别原则。每项必须引用确切的父原则名称并附覆盖理由。MUST 级别原则禁止在此处覆盖。 -->

### Override 1: VI. 合约化双协议标准接口 (SHOULD)

- **原始父规则**：所有对外能力通过 REST + MCP 双协议标准化接口发布，REST 覆盖通用系统集成与
  管理需求，MCP 原生适配 Agent 生态。

- **覆盖内容**：本 BC 作为内部 Core 域 BC，对外能力通过 **REST API（管理操作）+ Domain Object
  （BC 间内部调用）+ Spring ApplicationEvent（实体变更事件）** 三种接口发布，**不独立暴露 MCP
  协议**。MCP 协议的发布由 `agent-consumption` BC 统一负责，本 BC 的查询结果通过
  `semantic-query-engine` → `agent-consumption` 链路最终以 MCP 工具形式呈现给 Agent。

- **理由**：本 BC 在全局架构中定位为纯内部拓扑服务提供方，不直接面向 Agent 生态。MCP 的
  统一由 `agent-consumption` BC 发布是全局宪法 III（全链路权限过滤）的架构保障——若各 BC
  各自暴露 MCP，白名单过滤将无法集中执行。本覆盖与全局宪法 III 的 MUST 级要求完全一致。

### Override 2: VIII. Agent友好型输出 (SHOULD)

- **原始父规则**：所有查询与推理结果必须输出为低理解成本的结构化格式（如 JSON Schema、
  结构化上下文块），可直接注入 Agent 上下文，降低 Token 消耗与推理偏差。

- **覆盖内容**：本 BC 的查询输出目标为 **`semantic-query-engine`（内部域服务）** 和 **REST
  管理客户端**，返回标准 JSON 格式的关系实例数据。Agent 友好型的结构化上下文格式化由
  `agent-consumption` BC 在消费查询引擎结果时统一完成。本 BC 不直接生成 JSON Schema
  标注的 Agent 上下文块。

- **理由**：本 BC 处于语义网络拓扑的中间层，下游由 `semantic-query-engine` 进行查询聚合、
  `agent-consumption` 进行格式化与上下文封装。强制在本 BC 层输出 Agent 友好格式将导致
  格式化职责分散，增加一致性维护成本，且与全局架构设计中「Agent 消费接入层统一格式化」
  的分工矛盾。

**Feature Branch**: `001-relation-instance-lifecycle`

**Created**: 2026-07-29

**Status**: Draft

## Clarifications

### Session 2026-07-29

- Q: 什么构成「强依赖」应阻止关系下线？ → A: 仅目标关系被其他关系显式声明为依赖关系端点（relation-type 为依赖/必要条件类，如 "depends-on"、"requires"）时视为强依赖并拦截下线，其他关系类型（如 "contains"、"maps-to"）不影响下线。
- Q: 关系 FQN 三元组分隔符选择 `.` 还是 `#`？ → A: 采用 `#` 分隔符，格式为 `{源实体FQN}#{关系类型FQN}#{目标实体FQN}`
- Q: 跨 BC 事件传输机制，MVP 使用什么方案？ → A: 保持 MVP 使用 Spring ApplicationEvent，但定义抽象的 Domain Event 接口，预留 MQ 替换能力
- Q: "已生效版本的结构不可修改"的边界是什么？ → A: 仅历史版本记录本身不可修改（已有 Constitution VII 保障），允许基于历史版本创建新草稿后修改结构再重新生效，FR-019 保留
- Q: 跨 BC 引用关系查询接口协议？ → A: 双模——Domain Service 接口 + REST 端点，MVP 同进程直接调用，抽象层预留远程调用能力
- Q: 多维过滤应包含哪些维度？ → A: 关系类型、源/目标实体类型、源/目标实体 FQN（含前缀匹配）、RelationSchema FQN、name/description 关键词搜索、时间范围共 6 个维度（不含状态和 embedding）。各维度均支持多值集合匹配。
- Q: 多维过滤维间/维内组合语义？ → A: 维度间 AND，维度内 OR
- Q: 多维过滤接口形态？ → A: 新增统一多维过滤接口作为主查询入口，FR-029/030/031 保留作为简便快捷接口
- Q: name/description 文本搜索语义？ → A: 子串包含匹配（`ILIKE '%keyword%'`），配合 `pg_trgm` GIN 索引加速
- Q: embedding 向量相似度查询是否在 MVP 实现？ → A: 当前阶段不实现，移除对应 FR。embedding 字段保留在实体定义中，相似度查询后续迭代支持。
- Q: 完全新增关系实例的 FQN 如何生成？ → A: 必须通过统一 FQN 生成器生成，输入源实体FQN、关系类型FQN、目标实体FQN，禁止手动指定 FQN。适用于手动创建、自动构建、批量导入等所有新增路径。

### Session 2026-08-01

- Q: 关系实例变更事件应覆盖哪些状态转换？ → A: 覆盖 DRAFT→ACTIVE（生效）+ ACTIVE→DEPRECATED（下线）两种，重新生效复用激活事件。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 关系实例草稿编辑与版本生效 (Priority: P1)

领域知识工程师需要基于已发布的 RelationSchema 创建关系实例，经历草稿编辑、结构校验、
拓扑合法性校验后正式生效，成为语义网络中可被下游模块消费的正式拓扑数据。

**Why this priority**: 关系实例的全生命周期管理是本 BC 的核心职责。草稿编辑与版本生效
是关系数据写入正式环境的唯一入口，是所有下游查询、推理、拓扑遍历的数据基础。
没有此能力，语义关系网络无法建立。

**Independent Test**: 在已发布的 RelationSchema 约束下，创建一条关系草稿，
填写属性内容并通过结构校验后执行生效操作，验证主表中出现对应记录且历史表包含归档版本。

**Acceptance Scenarios**:

1. **Given** 元模型治理 BC 已发布包含关系类型约束的 RelationSchema v1.0，且源/目标实体
    均为生效状态，**When** 领域知识工程师基于该 Schema 新建关系草稿（输入源实体 FQN、
    关系类型 FQN、目标实体 FQN，由统一 FQN 生成器自动生成关系 FQN，再填写属性内容），**Then** 草稿成功写入草稿表，主表不受影响，草稿创建响应时间
    不超过 50ms（含结构校验）。

2. **Given** 关系草稿已存在且内容合法，**When** 领域知识工程师对草稿属性内容进行编辑保存，
   **Then** 系统自动执行 JSON Schema 结构校验，校验通过后草稿表更新，校验失败则返回
   包含违规字段路径和规则引用的结构化错误信息。

3. **Given** 关系草稿已通过所有校验（结构合规、端点有效、基数合法、元模型版本有效），
   **When** 领域知识工程师执行生效操作，**Then** 在同一事务内完成四步操作——主表写入/
   覆盖、历史表归档（版本号递增）、草稿表删除、双向索引更新——任一步失败全量回滚，
   不存在中间脏状态。

4. **Given** 同一 FQN 已存在一条生效关系，**When** 领域知识工程师基于该关系创建草稿后
   执行生效，**Then** 主表记录被全量覆盖，原版本归档至历史表，新版本成为唯一对外生效版本。

5. **Given** 草稿的 RelationSchema FQN 指向一个未发布或草稿态的元模型版本，
   **When** 领域知识工程师尝试创建草稿，**Then** 系统直接拦截并返回"元模型未发布"错误。

### User Story 2 - 实体生命周期驱动的自动关系构建 (Priority: P1)

当 metadata-management BC 发布实体生效或下线事件时，本 BC 自动解析实体属性中的元模型关系引用，
生成、更新或销毁对应的关系实例，保障实体与关系的拓扑一致性，无需人工介入。

**Why this priority**: 自动构建是语义网络拓扑完整性的核心保障机制。实体大批量创建时，
人工逐条建立关系不可行。此能力确保语义图谱的真正自动化沉淀。

**Independent Test**: 创建一个包含关联引用属性的实体并执行生效，验证系统自动生成对应的
关系实例，且关系 FQN 遵循 `{源实体FQN}#{关系类型FQN}#{目标实体FQN}` 格式。

**Acceptance Scenarios**:

1. **Given** 实体包含符合 RelationSchema 定义的关联引用字段，**When** 该实体生效，
   **Then** 系统自动解析关联引用，生成对应关系实例草稿并直接执行生效，
   关系 FQN 按自动命名规则生成。实体变更与关系变更在不同事务中完成，遵循最终一致性。

2. **Given** 已生效实体的关联属性发生变更后重新生效，**When** 变更涉及关系引用的新增、
   修改或移除，**Then** 系统自动增量对比变更前后的关联引用，对应新增/修改/销毁关系实例。

3. **Given** 实体被下线，**When** 该实体作为源端或目标端存在关联的生效关系，
   **Then** 系统自动触发关联关系的下线校验，不存在下游强依赖时同步下线对应关系；
   存在强依赖则记录异常并通知管理员。

4. **Given** 自动构建的关系实例涉及的端点实体类型不符合 RelationSchema 定义的端点约束，
   **When** 自动构建执行校验，**Then** 系统拦截该关系实例的构建并记录异常，不写入正式环境。

### User Story 3 - 多维关系查询与拓扑浏览 (Priority: P1)

领域知识工程师、业务分析人员需要通过多种方式查询生效关系：FQN 精准定位、指定实体出入边
浏览邻接拓扑、按关系类型或前缀范围批量查询。管理员还需要查询包括草稿在内的全部状态。

**Why this priority**: 查询是关系数据的消费入口，是下游 semantic-query-engine 进行图遍历、
推理、上下文生成的数据基础。没有查询能力，已构建的语义图谱无法被利用。

**Independent Test**: 在主表中存在多条生效关系的前提下，分别执行 FQN 精准查询、
指定实体的出边/入边查询、前缀范围查询，验证均能在性能基线内返回正确结果。

**Acceptance Scenarios**:

1. **Given** 主表中存在 FQN 为 "SalesOrder_001#COMPOSITION#OrderItem_003" 的生效关系，
   **When** 查询方通过该 FQN 发起精准查询，**Then** 系统在 20ms 内返回该关系的完整属性（含 name、description、embedding）、
   关联元模型 FQN、端点实体 FQN、当前版本号和审计信息。

2. **Given** 实体 FQN 为 "SalesOrder_001" 存在多条出边关系，**When** 查询方发起该实体
   的出边查询（可选按关系类型过滤），**Then** 系统基于双向索引在 50ms 内返回所有出边关系
   列表（百级结果集），每项包含 FQN、关系类型名称、目标实体 FQN、更新时间。

3. **Given** 系统中存在大量生效关系，**When** 查询方按 FQN 前缀或 RelationSchema 类型
   发起范围查询并指定分页与排序条件，**Then** 系统在 100ms 内返回分页结果列表。

4. **Given** 管理员需要查看草稿态与已下线的关系数据，**When** 管理员调用全状态查询接口，
   **Then** 系统从主表、草稿表、历史表分别聚合数据，返回结果中明确标注每条数据的来源表
   与当前状态。普通消费方调用该接口返回无权限错误。

### User Story 4 - 关系下线与历史版本追溯 (Priority: P2)

领域知识工程师需要对不再需要的关系执行下线操作，下线前系统自动校验依赖影响。
平台管理员和审计人员需要查阅所有曾经生效过的历史版本，支持单版本详情查看和任意两版本
差异对比。

**Why this priority**: 下线是关系生命周期的闭环操作，历史追溯是治理合规的基本要求。
但 MVP 阶段可先聚焦核心写入与查询链路，下线与追溯能力在 P1 稳定后增量交付。

**Independent Test**: 对一条已生效关系执行下线，验证该 FQN 在主表中被移除、对外查询返回
"不存在"状态、历史表保留该关系所有历史版本且不可篡改。

**Acceptance Scenarios**:

1. **Given** 一条已生效关系，**When** 领域知识工程师执行下线操作，**Then** 系统先执行
   依赖校验——存在下游强依赖时拦截下线并返回依赖清单，不存在强依赖时移除主表记录；
   历史表已归档的版本不受影响。

2. **Given** 实体被下线，**When** 系统检测到该实体关联的生效关系，**Then** 自动触发
   关联关系的下线校验流程，符合条件则同步下线。

3. **Given** 某关系曾经历过 3 次版本生效并存档于历史表，**When** 查询方按该关系 FQN
   请求历史版本列表，**Then** 系统在 100ms 内返回包含版本号、生效时间、变更人的倒序列表。

4. **Given** 同一 FQN 下存在两个历史版本（v1 和 v3），**When** 查询方请求两版本差异对比，
   **Then** 系统返回字段级差异，按"新增字段、修改字段、删除字段"分类，标注原值与新值。

5. **Given** 一条已下线的关系，**When** 领域知识工程师请求无需修改直接重新生效，
   **Then** 系统从历史表读取最新归档版本写入主表，版本号不变，历史表不新增记录。

### User Story 6 - 关系实例变更事件通知 (Priority: P1)

当关系实例的正式态发生变更（生效、下线）时，系统自动发布关系变更事件，
下游 BC（semantic-query-engine、agent-consumption）通过监听事件及时感知
语义图谱的拓扑变化，更新其内部缓存、索引或上下文数据，保障全平台语义一致性收敛。

**Why this priority**: 事件驱动是下游 BC 感知拓扑变化的唯一通道。若缺乏事件通知，
semantic-query-engine 的图遍历结果将停留在旧快照，agent-consumption
的上下文生成将包含过期关系数据，直接破坏全平台语义一致性。

**Independent Test**: 对一条关系草稿执行生效操作，验证事务提交后事件被成功发布，
下游测试监听器收到包含正确 FQN、变更类型和版本号的 RelationChangeEvent。

**Acceptance Scenarios**:

1. **Given** 一条关系草稿通过全量校验并执行生效操作且原子事务成功提交，
   **When** 事务提交完成，**Then** 系统以事务后回调方式发布 RelationChangeEvent
   （changeType = ACTIVATED），事件负载包含关系 FQN、当前版本号、RelationSchema FQN、
   源实体 FQN、目标实体 FQN 和事件产生时间戳。

2. **Given** 一条已生效关系执行下线操作且原子事务成功提交，
   **When** 事务提交完成，**Then** 系统发布 RelationChangeEvent
   （changeType = DEPRECATED），事件负载包含关系 FQN 和事件产生时间戳。

3. **Given** 生效事务中途失败（任一校验不通过）导致回滚，
   **When** 事务回滚，**Then** 系统不发布任何 RelationChangeEvent，杜绝脏通知。

4. **Given** 一条已归档关系重新生效，**When** 重新生效事务成功提交，
   **Then** 系统发布 RelationChangeEvent（changeType = ACTIVATED），
   事件版本号为原归档版本号，下游 BC 视为新生效关系处理。

5. **Given** 自动构建场景下实体生效触发的自动关系生效，**When** 关系自动生效成功，
   **Then** 系统同样发布 RelationChangeEvent（changeType = ACTIVATED），
   事件处理逻辑与手动生效一致，下游 BC 无需区分关系来源。

### User Story 5 - 批量导入导出 (Priority: P2)

领域知识工程师需要将一批关系实例以 YAML/JSON 格式批量导入系统（进入草稿态），
以及按指定范围导出生效关系用于数据迁移或备份。

**Why this priority**: 批量操作是提升数据迁移与初始化效率的工具，但 MVP 阶段逐条操作的
核心链路验证优先。在 P1 稳定后以批量能力提升运维效率。

**Independent Test**: 导出一组生效关系为 YAML 文件，将该文件重新导入系统，
验证所有关系进入草稿态且结构校验通过。

**Acceptance Scenarios**:

1. **Given** 一个包含 10 条关系定义的 YAML/JSON 文件，**When** 领域知识工程师执行批量导入，
   **Then** 逐条执行结构与拓扑校验，校验通过的关系写入草稿表，校验失败的关系记录到失败清单
   （含 FQN、失败原因），合法数据不受非法数据影响。

2. **Given** 导入文件中存在与主表已有 FQN 重复的记录，**When** 采用"跳过"策略导入，
   **Then** 系统跳过重复项并记录到跳过清单；采用"报错"策略则对重复项标记错误。

3. **Given** 批量导入全部进入草稿态，**When** 导入完成后查询主表，**Then** 主表无任何变更，
   导入的关系不可被外部消费。需手动逐条执行生效方可对外可见。

4. **Given** 系统中存在 50 条生效关系，**When** 领域知识工程师按关系类型或 FQN 前缀
   导出为 YAML 格式，**Then** 导出文件包含每条关系的完整属性、关联元模型 FQN、端点实体
   FQN、当前版本号，且该文件可直接重新导入。

### Edge Cases

- 同一 FQN 同时存在草稿时，再次创建草稿应被拦截（单草稿限制），返回"已存在草稿"错误。
- 同一 RelationSchema 下同一源实体与同一目标实体的重复关系创建应被拦截。
- FQN 生成器生成的关系 FQN 与已有生效关系或草稿 FQN 冲突——拦截创建并返回"关系已存在"错误。
- 草稿生效时源实体或目标实体已下线——应拦截生效并返回明确端点不可用错误。
- 基数约束被违反时（如源端基数=1 但已存在同类关系）——拦截生效并返回基数违规详情。
- 跨 Bundle 关系创建时目标 Bundle 未授权——拦截创建并返回跨域权限不足错误。
- 并发场景下两个操作同时对同一 FQN 执行生效——采用最后写入覆盖策略（Last-Write-Wins），后提交的事务覆盖前者的结果。
- 批量导入 500 条关系中单条超过 10MB 的 content 字段——应拒绝该条并继续处理其余。
- 多维过滤查询指定了互斥或全空维度组合——返回空结果集，不报错。
- 多维过滤中 name/description 关键词包含 SQL 特殊字符——应做参数化查询防注入，关键词原样匹配。
- 多维过滤分页超出有效范围（page 过大）——返回空列表而非报错。
- 关系变更事件消费方处理失败（如下游 BC 抛异常）——不影响已提交的关系变更事务，
  不进行事件重试（MVP 无 MQ 持久化能力），需下游自行做幂等补偿。
- 同一关系短时间内连续生效两次（先草稿生效生成 v2，再基于 v2 创建草稿生效生成 v3）——
  每次生效独立发布 ACTIVATED 事件，下游通过版本号区分。
- 元数据变更事件中实体 FQN 无任何关联引用字段——监听器正确处理空关联场景，
  不生成任何关系实例，也不抛出异常。
- 元数据变更事件重复投递（相同 fqn + version）——监听器通过幂等键去重，
  不产生重复关系实例或重复下线操作。

## Requirements *(mandatory)*

### Functional Requirements

**草稿管理域**

- **FR-001**: 系统必须支持基于已发布的 RelationSchema（含完整版本号）手动新建关系草稿。
   创建时由统一 FQN 生成器根据源实体 FQN、关系类型 FQN、目标实体 FQN 自动生成关系 FQN，
   禁止用户手动指定 FQN。同时校验元模型版本存在且为已发布状态。
- **FR-002**: 系统必须支持基于已生效关系创建新草稿（草稿内容初始化为生效版本副本）。
- **FR-003**: 系统必须允许对草稿态关系的属性内容（content）进行编辑，编辑时实时执行
  JSON Schema 结构校验，校验不通过则拒绝保存并返回结构化错误信息。
- **FR-004**: 系统必须禁止修改草稿的 FQN（由生成器统一生成，创建后不可变更）、
  关联元模型版本、源/目标端点字段。
- **FR-005**: 系统必须支持草稿的物理删除操作（仅限草稿态），删除后该 FQN 可重新创建草稿。
- **FR-006**: 系统必须确保同一关系 FQN 最多仅允许存在一条草稿记录。
- **FR-007**: 草稿创建时必须校验源/目标实体 FQN 真实存在且为生效状态，否则拦截创建。
- **FR-008**: 草稿创建时必须校验关系类型与端点实体类型的匹配性，不符合 RelationSchema
  定义的端点类型则拦截。

**自动构建域**

- **FR-009**: 系统必须在实体生效事件触发时自动解析实体属性中的关联引用字段，
  生成对应关系实例并执行自动生效。
- **FR-010**: 系统必须在实体属性更新并重新生效时自动增量对比关联引用变更，
  对应新增/修改/销毁关系实例。
- **FR-011**: 系统必须在实体下线时自动触发该实体关联的所有生效关系的下线校验流程。
- **FR-012**: 自动构建必须遵循统一的 FQN 生成规则：
  `{源实体FQN}#{关系类型FQN}#{目标实体FQN}`。
- **FR-013**: 自动构建遵循最终一致性语义：实体变更发生在 metadata-management BC 的
   事务中，关系变更由本 BC 监听实体变更事件后在本 BC 的独立事务中异步完成。
   实体变更与关系变更不共享同一数据库事务。

**版本生效与下线域**

- **FR-014**: 草稿生效必须在单一数据库事务中原子完成四步操作：主表写入/覆盖、
  历史表归档（版本号递增）、草稿表删除、双向索引更新。任一步失败全量回滚。
- **FR-015**: 生效前必须执行全量校验：结构合规校验、端点有效性校验、基数合规校验、
  元模型版本有效性校验。
- **FR-016**: 系统必须在关系实例发生状态转变（涉及正式态的变更）时发布关系变更事件，
   通知下游模块（semantic-query-engine、agent-consumption）同步拓扑数据。
   事件类型覆盖两类：生效（DRAFT → ACTIVE）、下线（ACTIVE → DEPRECATED）。
   重新生效（ARCHIVED → ACTIVE）复用生效事件类型。
- **FR-016a**: 关系变更事件必须包含以下核心负载：关系 FQN、变更类型（ACTIVATED / DEPRECATED）、
   当前版本号、事件产生时间戳、关联的 RelationSchema FQN、源实体 FQN、目标实体 FQN。
- **FR-016b**: 关系变更事件必须在原子事务成功提交后发布；事务回滚时不得发布任何事件，
   杜绝脏通知。
- **FR-016c**: 系统必须定义抽象的关系变更事件接口（RelationChangeEvent），
   解耦事件发布方与消费方。MVP 阶段使用 Spring ApplicationEvent 实现，
   接口抽象层预留后续替换为消息队列（RabbitMQ/Kafka）的能力。
   事件消费方（下游 BC）通过实现 RelationChangeListener 接口或
   Spring @EventListener 注解进行消费。
- **FR-017**: 系统必须支持下线已生效关系，下线前执行依赖校验——
   仅当目标关系被其他关系显式声明为 DEPENDENCY_INFLUENCE 类型时视为强依赖并拦截下线并返回依赖清单；
   其他关系类型（如 COMPOSITION、MAPPING_CORRESPONDENCE）不阻断下线。
- **FR-018**: 下线操作必须是原子事务：删除主表记录、同步移除双向索引记录，历史表不做任何修改。
- **FR-019**: 系统必须支持基于历史归档版本重新生效，包括直接重新生效和修改后重新生效
  两种模式。

**双向索引与拓扑管控域**

- **FR-020**: 系统必须在关系生效时自动在源实体出边索引和目标实体入边索引中新增对应记录。
- **FR-021**: 系统必须在关系下线时自动从源实体出边索引和目标实体入边索引中移除对应记录。
- **FR-022**: 索引更新必须与关系生命周期变更是同一数据库事务。
- **FR-023**: 系统必须基于 RelationSchema 定义的基数约束在生效时实时校验，超出约束则拦截。
- **FR-024**: 系统必须支持按 FQN 前缀、关系类型发起批量拓扑完整性校验，
  检测悬空边、无效端点、基数异常、元模型不匹配四类问题并输出校验报告。

**结构合规校验域**

- **FR-025**: 系统必须在每次写入操作（创建草稿、编辑草稿、草稿生效、批量导入）时执行
  对应版本 RelationSchema 的 JSON Schema 全字段结构校验。
- **FR-026**: 校验必须覆盖字段类型、必填项、枚举值、取值范围、正则格式、数组元素约束。
- **FR-027**: 校验失败必须返回结构化错误信息，包含违规字段路径、违规类型、违反的元模型规则引用。
- **FR-028**: 校验逻辑必须与元模型版本严格绑定，版本升级不影响存量历史版本校验结果。

**查询检索域**

- **FR-029**: 系统必须支持通过 FQN 精准查询单条生效关系，返回完整属性（含 name、description、embedding）、
  关联元模型、端点信息和审计信息。此接口作为简便快捷入口保留。
- **FR-030**: 系统必须支持指定实体 FQN 分别查询其出边关系、入边关系或全部关联关系，
  支持按关系类型、目标实体类型过滤。此接口作为简便快捷入口保留。
- **FR-031**: 系统必须支持按 FQN 前缀、RelationSchema 类型组合条件查询生效关系列表，
  支持分页与排序。此接口作为简便快捷入口保留。
- **FR-032**: 系统必须提供管理端全状态查询接口（草稿 + 生效 + 下线），
  仅管理员角色可调用，普通消费方调用返回无权限错误。
- **FR-033**: 所有对外查询默认仅返回生效态关系，基于授权范围过滤结果。

**多维过滤域**

- **FR-047**: 系统必须提供统一的多维过滤查询接口，支持以下维度任意组合过滤（维度间 AND，维度内 OR）：
  - 关系类型（多值 IN，如 `COMPOSITION, DEPENDENCY_INFLUENCE`）
  - 源实体类型 / 目标实体类型（多值 IN）
  - 源实体 FQN / 目标实体 FQN（多值 IN + 前缀匹配）
  - RelationSchema FQN（多值 IN）
  - name / description 关键词（子串包含匹配 `ILIKE '%keyword%'`）
  - 时间范围（created_at / updated_at 区间）
- **FR-048**: 多维过滤接口必须支持分页（page/size）和排序（按 created_at、updated_at、name 等字段升/降序）。
- **FR-049**: 多维过滤查询默认仅查询主表生效态关系。管理端可通过参数切换至全状态查询（草稿 + 生效 + 下线），普通用户无全状态查询权限。
- **FR-050**: name/description 文本搜索采用子串包含匹配（`ILIKE '%keyword%'`），配合 PostgreSQL `pg_trgm` 扩展的 GIN 索引加速查询。

**历史版本追溯域**

- **FR-034**: 系统必须支持按 FQN 查询该关系的所有历史正式版本列表，按版本号倒序排列。
- **FR-035**: 系统必须支持按 FQN + 版本号查询对应历史版本的完整属性与端点信息。
- **FR-036**: 系统必须支持同一 FQN 下任意两个历史版本的字段级差异对比，
  按新增/修改/删除字段分类展示。

**批量导入导出域**

- **FR-037**: 系统必须支持 YAML/JSON 格式批量导入关系实例，导入默认进入草稿态，
   禁止直接写入主表。导入时 FQN 由统一生成器根据每条记录的源实体 FQN、关系类型 FQN、
   目标实体 FQN 重新生成，忽略导入文件中的 FQN 字段。
- **FR-038**: 批量导入必须支持"跳过"和"报错"两种幂等策略处理 FQN 重复。
- **FR-039**: 批量导入必须逐条校验，单条失败不影响其他合法数据，最终返回成功/失败清单。
- **FR-040**: 系统必须支持按 FQN 前缀、关系类型、指定 FQN 列表三种粒度导出生效关系。

**FQN 生成器域**

- **FR-041**: 系统必须提供统一的 FQN 生成器，接受源实体 FQN、关系类型 FQN、目标实体 FQN
  三个输入参数，按 `{源实体FQN}#{关系类型FQN}#{目标实体FQN}` 格式自动生成关系 FQN。
  所有完全新增关系实例的 FQN 必须通过该生成器统一生成，禁止手动构造 FQN。
- **FR-042**: FQN 生成器必须支持解析功能，能从关系 FQN 中解析出源实体 FQN、关系类型 FQN、
  目标实体 FQN 三个分量。

**跨 BC 集成域**

- **FR-043**: 系统必须定义抽象的 Domain Event 接口，用于解耦 metadata-management BC 的
   实体变更事件与 graph BC 的事件处理逻辑。MVP 阶段使用 Spring ApplicationEvent 实现，
   接口抽象层预留后续替换为消息队列（RabbitMQ/Kafka）的能力。
- **FR-044**: 系统必须实现元数据变更事件监听器（MetadataChangeListener），
   响应 metadata-management BC 发布的 MetadataChangeEvent，按变更类型执行对应处理：
   - **实体生效（ACTIVATE）**：自动解析实体属性中的关联引用字段，基于 RelationSchema
     关系约束生成对应关系实例草稿并执行自动生效；实体变更与关系变更在不同事务中完成，
     遵循最终一致性。
   - **实体更新（ACTIVATE，再次生效）**：增量对比变更前后的关联引用，对应新增/修改/销毁
     关系实例；自动构建的关系实例与手动创建遵循相同的 FQN 规则与校验流程。
   - **实体下线（DEPRECATE）**：自动触发该实体作为源端或目标端的所有生效关系的下线校验流程。
     不存在下游强依赖时同步下线对应关系并发布 DEPRECATED 事件；
     存在强依赖则记录异常并阻止下线。
- **FR-044a**: 元数据变更事件监听器必须实现幂等处理机制，以事件中的实体 FQN + 版本号
   为幂等键，避免重复事件导致的关系重复构建或误删。
- **FR-044b**: 监听器必须在 metaforge-graph-core 模块中实现，通过依赖
   metaforge-metadata-api 模块引入 MetadataChangeListener 接口与 MetadataChangeEvent 事件类型，
   禁止直接依赖 metaforge-metadata-core 模块。
- **FR-045**: 系统必须对外提供引用关系查询接口（Domain Service 接口 + REST 端点），
   允许 metadata-management BC 查询指定实体是否存在关联的依赖关系。
   MVP 阶段 metadata-management BC 通过 Domain Service 同进程调用该接口，
   接口抽象层预留远程 REST 调用能力。

**版本不可变域**

- **FR-046**: 关系生效后，已生效的历史版本记录本身不可修改（仅允许 INSERT）。
  允许基于历史版本创建新草稿后修改结构再重新生效。禁止对历史表执行 UPDATE 或 DELETE 操作。

### Key Entities

- **关系实例 (Relation Instance)**: 语义网络中两个元数据实体之间的有向关联，承载关系
   类型（依赖/从属/映射/约束）、源实体、目标实体、属性内容（JSONB，遵循 RelationSchema
   的 JSON Schema 结构），以及版本号、审计信息。包含 name（人类可读名）、description（描述）、
   embedding（向量嵌入，JSONB 对应 `List<Float>`）。是主表的唯一聚合根。
- **关系草稿 (Relation Draft)**: 关系实例的编辑态副本，与正式版本物理隔离。包含与关系实例
   相同的基础字段（name、description、embedding、content 等）。仅存在于
   草稿表，对外完全不可见。可被编辑和删除，生效后迁移至主表成为正式版本。
- **关系历史版本 (Relation Version)**: 曾经正式生效过的关系版本快照。包含 name、description、
   embedding 全量快照。仅存在于历史表，
   仅支持新增（INSERT），不可修改或删除。用于版本追溯与差异对比。
- **双向引用索引 (Entity Relation Index)**: 为每个元数据实体维护的出边关系列表（以该实体
   为源端）和入边关系列表（以该实体为目标端），随关系生命周期同步更新。
- **关系变更事件 (Relation Change Event)**: 关系实例正式态变更时发布的域事件。包含关系 FQN、
   变更类型（ACTIVATED / DEPRECATED）、当前版本号、RelationSchema FQN、源实体 FQN、
   目标实体 FQN 和事件时间戳。继承 Spring ApplicationEvent，在原子事务成功提交后发布，
   事务回滚不发布。供下游 BC（semantic-query-engine、agent-consumption）监听消费。

### Relation Types

关联类型枚举，仅允许以下五种类型：

| 枚举值 | 说明 |
|--------|------|
| `COMPOSITION` | 组成——表示整体与部分的结构化关系 |
| `ASSOCIATION_REFERENCE` | 关联引用——实体间的通用引用关系 |
| `MAPPING_CORRESPONDENCE` | 映射对应——不同领域实体间的映射关系 |
| `DEPENDENCY_INFLUENCE` | 依赖影响——表达实体间的依赖与影响链路 |
| `PROCESS_SEQUENCE` | 流程时序——表达实体在流程中的先后顺序关系 |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 领域知识工程师能在 50ms 内完成单条关系草稿的创建（含 JSON Schema 结构校验）。
- **SC-002**: 对主表中的生效关系执行 FQN 精准查询，响应时间不超过 20ms。
- **SC-003**: 对单实体执行出入边查询（百级结果集），响应时间不超过 50ms。
- **SC-004**: 500 条关系实例的批量导入（含逐条结构校验）能在 6 秒内完成。
- **SC-005**: 草稿生效的原子四步事务操作响应时间不超过 100ms。
- **SC-006**: 结构合规校验通过率达到 100%——任何不符合 RelationSchema 约束的数据无法写入
  主表或草稿表。
- **SC-007**: 双向索引数据与主表正式数据完全一致——生效/下线操作后索引记录零遗漏、零冗余。
- **SC-008**: 实体下线时，该实体关联的所有生效关系在 100ms 内完成下线校验与同步处理，
  零悬空边残留。
- **SC-009**: 单 FQN 的全历史版本列表查询响应时间不超过 100ms。
- **SC-010**: 所有写入操作的元模型约束引用准确率 100%——无错绑、漏绑元模型版本。
- **SC-011**: 多维过滤查询（含 3 个维度组合、百级结果集）响应时间不超过 100ms。

## Assumptions

- 元模型治理 BC 已稳定提供 RelationSchema 的查询接口，本 BC 不负责元模型校验逻辑的实现。
- metadata-management BC 已实现实体生命周期事件（生效/下线/更新）的发布机制，
  本 BC 通过抽象 Domain Event 接口监听事件。MVP 阶段使用 Spring ApplicationEvent
  同步实现，接口抽象层预留后续替换为消息队列（RabbitMQ/Kafka）的能力。
- 源/目标实体的可见性权限由上游模块控制，本 BC 在创建关系时仅校验实体存在性与生效状态，
  不做权限判断。关系的权限过滤在查询时由 agent-consumption BC 统一执行。
- 本 BC 使用 PostgreSQL `semantic_relation_network` Schema，与其他 BC 通过独立 Schema 隔离。
- MVP 阶段不引入消息队列，BC 间通信使用 Spring ApplicationEvent 同步传递 Domain Event。
  后续可基于 Domain Event 接口抽象层替换为消息队列实现。
- MVP 阶段单租户部署，不涉及多租户数据隔离。
- 关系元模型版本绑定创建后不可变更——RelationSchema 升级后存量关系不自动适配新版本。
- metadata-management BC 与 metaforge-graph BC 分属不同 PostgreSQL Schema 甚至不同服务，
  无法共享同一数据库事务。跨 BC 的实体变更→关系同步采用最终一致性语义，
  自动构建（FR-009~FR-013）中的实体变更与关系变更在不同事务中独立完成。
- name/description 文本搜索依赖 PostgreSQL `pg_trgm` 扩展提供 trigram GIN 索引加速，
  MVP 阶段不引入外部搜索引擎（如 Elasticsearch）。

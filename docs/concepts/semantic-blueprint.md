# 语义说明书范式

MetaForge 不存储任何具体业务数据，而是存储"数据的数据"——客观业务世界的**语义说明书**，统一描述业务领域内的概念定义、语义关系、规则约束与能力边界。

## 语义说明书 = 结构化元数据

MetaForge 的技术本质是**元数据驱动**：一切语义以元数据为唯一载体，分三层沉淀：

```
元模型（M2）     定义"语义长什么样"——Bundle/实体类型/关系/规则的结构模板
   ↓ 实例化
元数据（M1）     填充"具体语义"——领域概念、规则定义、能力描述、对象结构
   ↓ 关联
语义关系网络     连接"语义与语义"——组成/引用/流程/决策等关系的语义图谱
```

- **元模型**：声明式定义（Bundle → Package → 实体类型/关系类型），是语义规则的唯一底座
- **元数据**：遵循元模型结构约束的领域语义实例（含 L3-L5 业务对象结构、规则阈值）
- **语义关系网络**：自动校验并构建实体间关联，沉淀完整语义图谱

Agent 消费的"说明书"，就是这套元数据经认知模板组织后的输出。**全链路只处理元数据，不触碰任何具体业务数据**——这是 MetaForge 的边界，也是它能跨系统通用的原因。

## 数据 vs 说明书

用一句话区分两者：

> **数据是流水，说明书是航道。**

| | 业务数据（实例值） | 语义说明书（元数据） |
|---|-------------------|---------------------|
| 例子 | 订单 RX-002 剂量 800mg | 规则：单次剂量 > 500mg 须转药师复核 |
| 变化 | 每笔业务都在变 | 长期稳定，仅在业务规则调整时更新 |
| 归属 | 各业务系统的运行时数据 | 统一治理的语义层 |
| 谁消费 | 业务应用 | AI Agent |

MetaForge 只存右侧的"说明书"：**阈值定义、对象结构、关系语义、能力边界**——而不存左侧任何具体值。"这笔订单超没超限"由 Agent 执行时读数据对照说明书得出。

## 语义说明书的四要素

一套完整的业务语义说明书，包含四类内容：

1. **概念定义**：业务领域有哪些对象、什么含义（如"处方""机柜""供应商"）
2. **语义关系**：对象之间如何关联（组成、引用、流程先后、决策分支）
3. **规则约束**：什么条件下必须/应该做什么（阈值、强制约束、边界）
4. **能力边界**：对象能用什么工具/能力，Agent 的执行权限边界

这四类内容全部以**元数据**形态沉淀——概念是元数据实体、关系是关系实例、规则是规则元数据、能力是能力元数据，统一受元模型结构约束。

## 业务对象结构：表结构作为元数据

MetaForge 用四级层次（L3-L5）把"业务对象长什么样"也建模为说明书：

```
业务对象 (L3)  —— 如：处方表 / 库存快照表 / 机柜遥测表
  └─ 逻辑实体 (L4) —— 表的逻辑落地（字段集）
       └─ 属性 (L5) —— 字段定义（字段名、类型、单位）
```

这让 Agent 在接触任何业务数据前，就知道"数据有哪些字段、各是什么类型单位"——**结构本身可查询、可建模**，Agent 无需猜测数据形状。

## 规则阈值语义化

说明书中存的是**规则定义与阈值**，而不是具体值：

```
Rule_DosageLimit: 单次剂量 > 500mg 且 药物=acetaminophen → 转药师复核  (MANDATORY)
```

- 说明书存"500mg 这个阈值定义"
- 不存"RX-002 是 800mg"（那是业务数据）
- 执行时：Agent 读 RX-002 的 800mg，对照说明书阈值 → 判定"触发复核"

**同一份说明书，对不同数据值，产生不同且正确的结论**——这正是语义说明书指导执行的精髓。

## 与 RAG / 向量库 / 规则引擎的区别

| | 方案 | 差异 |
|---|------|------|
| **RAG** | 检索业务文档片段 | 给 Agent 的是碎片化文本，无结构化语义，可能过时/矛盾 |
| **向量库** | 语义相似度检索 | 返回"相似片段"，不是"权威规则"，可解释性弱 |
| **规则引擎** | 硬编码业务规则 | 规则散落代码、不可查询、不可被 Agent 消费 |
| **MetaForge** | 统一语义说明书 | 结构化、可查询、可版本治理、可解释，专为 Agent 消费设计 |

MetaForge 不是"给 Agent 更多上下文"，而是"给 Agent 正确的、可依据的语义"。

## 元数据治理

元数据不是一堆散落的条目，而是可治理的语义资产：

- **版本管控**：以 Bundle 为单元整体固化版本，语义随版本统一迭代，不漂移
- **结构约束**：所有元数据严格遵循元模型定义的结构，保障规范性、消除语义分歧
- **生命周期**：元数据经历创建 → 草稿 → 激活 → 发布 → 版本演进，全程可管控、可追溯
- **边界管控**：导出清单明确命名空间边界，未暴露的语义对消费方不可见

正因为"语义即元数据、元数据可治理"，Agent 的认知才是**可控、可更新、可审计**的——而不是依赖不可控的模型先验。

## 自建语义库（元模型 Bundle）

MetaForge 内置 agent 语义库（Bundle `metaforge:1.0.0`）开箱即用；更关键的是——**使用者可以自建自己的语义库**：

```
创建 Bundle → 定义实体类型/关系/规则 → 填充语义说明书实例 → 发布版本 → 认知模板按 scope 消费
```

- 不同业务场景建不同的 Bundle，**多库并存、按需消费**（`scope.bundles` 指定）
- 元模型接口（REST）完整支持 Bundle/EntitySchema/RelationSchema 的创建与治理
- 如同数据库既自带系统库、也允许你建自己的业务库

> MetaForge 是"语义库的库"——内置 agent 语义库即开即用，更支持按业务自建，一套底座适配无限场景。
